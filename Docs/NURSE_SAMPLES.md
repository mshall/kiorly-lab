# Nurse-collected samples (KLORD05, KNLAB01, KLORD02, KLCRIT02)

Kiorly Nurse is an **edition of Kiorly Clinic** (ADR-031): there is no `kiorly-nurse` repository, client or endpoint set. A nurse visit that records a lab order and collects a sample hands it to Kiorly Lab through the same Clinic -> Kiorex -> Lab path as KCV204.

## Flow
1. **Nurse side (Kiorly Clinic, NURSE edition; Pro+)**: visit record -> lab order -> sample collection (tube labels, collection time, temperature, two verified identifiers) -> hand-over. The Clinic emits `LabOrderPlaced` (kiorex-contracts 1.6.0; carries ids, `consentToken` = the patient's LAB_RESULTS record-share grant, ordered items, `preferredLabId` and, since 1.6.0, the ratified optional Nurse fields `originEdition: "NURSE"`, `prescriberName`, `identifiersChecked`, `patient` (minimum demographics) and `nurseCollection`). Implemented in clinics-management (`apps/api/src/nurse/lab-sample.service.ts`, `Docs/NURSE_EDITION.md`).
2. **Kiorex** relays it to the lab with a second registration holding the lab's `KIORLY_NURSE` integration client (HMAC, same scheme as Kiorex bookings; Kiorex `src/lab/nurse-lab-relay.service.ts`): `POST /api/v1/integration/v1/orders`. `src/integration/nurse-handoff.ts` (`labOrderPlacedToInbound`) is the reference mapping and is exercised by the tests, which also validate the result against the ratified contract schema: `orderId -> sourceRef`, `patientRef -> patient.externalId`, `patient -> patient`, `items[].code -> testCodes`, `consentToken -> nurseCollection.consentToken`, `nurseCollection`, `identifiersChecked`, `preferredLabId -> labId`, `orderingClinicianId` + `prescriberName -> referringDoctor`.
3. **Lab ingest** (`OrdersService.create`, source `KIORLY_NURSE`, idempotent on `(org, source, sourceRef)`): refuses without a consent token (400/422 `CONSENT_REQUIRED`), without two identifiers (422 `TWO_IDENTIFIERS_REQUIRED`), with a future collection time (422 `COLLECTED_IN_FUTURE`) or a hand-over outside collection..now (422 `HANDOVER_TIME_INVALID`), with samples that do not match the ordered tests (422 `SAMPLE_MISSING_FOR_TEST`, `SAMPLE_UNMATCHED`, `SAMPLE_DUPLICATE_GROUP`) and for duplicate tube labels (409 `ACCESSION_DUPLICATE`, the whole ingest rolls back).
4. **Chain of custody starts at the nurse's collection time**: one specimen per (type, container) group, `barcode = the nurse's tube label` (so the physical label is what the lab scans at receipt), `accessionNumber = lab-generated`, status `COLLECTED` (or `IN_TRANSIT` when a hand-over time is given); custody `COLLECTED` at `collectedAt` (actor `nurse:<collectorRef>`, with temperature), then `TRANSPORT_STARTED` at hand-over. The order is `COLLECTED` and no home address ever reaches the lab.
5. **Receipt**: the usual `POST /specimens/:id/receive` with the scanned label; a wrong scan is blocked and recorded (`LABEL_MISMATCH_BLOCKED`); `RECEIVED` records the transit time since the nurse's collection and sets `NurseCollection.receivedAt`. Rejection creates a re-collection specimen as for any order (re-collection happens in the lab).
6. **Release (KLCRIT02)**: consent channels default to `KIORLY_NURSE_IMPORT` (+ whatever the relay sent); the report can be released on that channel only if consented (`CONSENT_REQUIRED` otherwise); the nurse fetches it with `GET /integration/v1/reports/:id/pdf` (403 until released on its channel; a Kiorex vault client cannot fetch it). The `LabResultReleased` contract channel for the Nurse edition is `KIORLY_CLINIC`.
7. **Custody view for the nurse**: `GET /integration/v1/orders/:sourceRef/custody` (nurse / clinic clients, own orders): event type, time, temperature, `by: NURSE | LAB`; no names, no PHI.

## Data and privacy
`NurseCollection` stores visit reference, collector reference (never a phone or national id), times, temperature and **only the SHA-256 of the consent token**. Audit rows carry ids/counts only. `LabOrderCreated` / `LabOrderStatusChanged` go to Kiorex with `source: "KIORLY_CLINIC"` (contract enum) and the ratified optional `originEdition: "NURSE"` (contracts 1.6.0). Kiorex relays them (with this custody read) to the nurse's clinic as status pushes.

## Contract status (ratified in kiorex-contracts 1.6.0)
`nurseCollection`, `identifiersChecked` (>= 2 distinct kinds from `fullName | dateOfBirth | phone | nationalId | externalId`; `fullName` is accepted for nurse intake only and is the one lab-side vocabulary extension), `collection.districtId`, the `KIORLY_NURSE` client source (`x-client-sources`), the `LabOrderCustody` read and the optional `originEdition` on the Lab events are in `kiorly-lab.v1.openapi.json` 0.3.0 / the event schemas. The inbound order stays strict (`additionalProperties: false`) except for those fields; `test/nurse-samples.e2e.test.ts` checks both the relay body and the lab's own validator against the contract schema. Dev client `kl_dev_nurse / dev_nurse_secret_change_me` is created by `npm run db:seed` (local only).

## Open items (NH-LB-034)
- Consent token verification against Kiorex (token still valid / not revoked) is mocked: the Lab checks presence and stores the hash. Kiorex checks local revocation for linked patients and the clinic mints the token; real verification is a provider go-live item.
- Specimen stability/transit limits are clinical: the Lab records the transit minutes but does not auto-reject (pathologist decision).
- Tube-label format: 3-40 printable ASCII characters, unique per lab (now part of the contract pattern).
- Production needs a `KIORLY_NURSE` integration client per lab tenant that accepts nurse samples (lab owner: `POST /integration-clients {"source":"KIORLY_NURSE"}`), registered in Kiorex as partner kind `lab_nurse`.
